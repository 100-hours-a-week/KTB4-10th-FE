# 기술 검토 및 스택 선정

> 현재 선택과 선택 이유를 기록하는 초안이다. 라이브러리는 실제 반복 문제가 확인될 때 추가한다.

## 1. 선택 기술

| 구분 | 선택 | 이유 | 비교 대상 |
|---|---|---|---|
| UI | React 19 | 컴포넌트 기반 화면 구성과 팀 학습 자료가 풍부하다. | Vue, Svelte |
| 언어 | TypeScript | API DTO와 화면 상태의 오류를 실행 전에 발견한다. | JavaScript |
| 빌드 | Vite 8 | 개발 서버와 빌드가 단순하고 빠르다. | CRA, Next.js |
| 라우팅 | React Router 7 | SPA의 인증·회원 상태별 경로를 명시적으로 관리한다. | 직접 History API 처리 |
| HTTP | Axios | credentials, XSRF, interceptor 설정을 공통화하기 쉽다. | fetch |
| 테스트 | Vitest + Testing Library | Vite와 결합이 간단하고 사용자 관점 UI 테스트에 적합하다. | Jest |
| 린트 | Oxlint | 초기 설정이 작고 빠르다. | ESLint |

## 2. 지금 도입하지 않는 기술

- 전역 상태 관리: 로그인 회원처럼 전역 공유 상태가 실제로 늘어날 때 검토한다.
- 서버 상태 라이브러리: 캐시·재검증·중복 요청 제어가 반복될 때 TanStack Query를 검토한다.
- UI 프레임워크: Figma V1 스타일을 구현한 뒤 반복 컴포넌트가 확인되면 검토한다.
- SSR 프레임워크: 현재는 로그인 이후 사용하는 웹앱이 중심이므로 SPA로 시작한다.
- PWA: 현재는 브라우저 기반 모바일 웹 앱으로 시작하고, 설치·오프라인·백그라운드 알림 요구가 확정될 때 검토한다.
- 데스크톱 UI 프레임워크: V1부터 V3까지 모바일 앱 셸을 유지하므로 별도의 데스크톱 레이아웃 체계는 도입하지 않는다.
- SSE/Web Push/FCM: V1 인앱 알림 조회와 별개이며 전달 채널 요구가 확정될 때 도입한다.

## 3. 선택 기준

1. V1 요구사항을 가장 작은 의존성으로 구현할 수 있는가?
2. 팀원이 설정과 장애 원인을 설명할 수 있는가?
3. 백엔드의 세션·CSRF 계약을 안전하게 지원하는가?
4. 교체 비용보다 현재 얻는 이점이 큰가?

## 4. 재검토 시점

- API 호출별 로딩·캐시 코드가 반복되면 서버 상태 라이브러리를 검토한다.
- 서로 먼 화면에서 같은 상태를 수정하면 전역 상태 도입을 검토한다.
- 검색 노출이나 첫 화면 응답이 핵심 지표가 되면 SSR을 검토한다.
