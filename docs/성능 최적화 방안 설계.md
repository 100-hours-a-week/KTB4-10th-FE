# 성능 최적화 방안 설계

> 측정 없이 복잡한 최적화를 먼저 넣지 않는다. V1 기준선과 병목 발생 시 대응 순서를 정한다.

## 1. 목표 지표

- Core Web Vitals: LCP, INP, CLS를 배포 환경에서 측정한다.
- API: 주요 화면별 요청 시간과 실패율을 확인한다.
- 번들: 초기 JavaScript 크기와 화면별 chunk를 빌드 결과에서 확인한다.

## 2. V1 기본 적용

- 라우트 단위 코드 분할로 최초 진입에 필요 없는 화면을 지연 로딩한다.
- 이미지 크기와 포맷을 화면에 맞추고 lazy loading을 사용한다.
- 가이드북 상태 폴링은 앱 전역에서 유지하고 완료·실패·취소·앱 종료 시 중단한다. 내부 화면 전환은 중단 조건이 아니다.
- 검색 입력은 debounce하고 같은 조건의 불필요한 중복 요청을 피한다.
- 목록에는 서버 페이지네이션을 사용하고 대량 데이터를 한 번에 렌더링하지 않는다.
- 컴포넌트 재렌더링은 프로파일링 결과가 있을 때 최적화한다.
- 데스크톱에서도 모바일 앱 셸만 렌더링하며 데스크톱 전용 대형 이미지나 중복 레이아웃 자산을 내려받지 않는다.
- `100dvh`와 안전 영역을 사용해 모바일 주소창·노치 변화로 인한 불필요한 레이아웃 이동을 줄인다.

## 3. 단계별 검토

| 징후 | 먼저 확인 | 이후 선택지 |
|---|---|---|
| 초기 화면이 느림 | 번들 분석, 이미지, 폰트 | route lazy loading, asset 최적화 |
| 같은 API가 반복됨 | 호출 주체와 화면 수명 | 요청 병합, TanStack Query 캐시 |
| 긴 목록이 버벅임 | DOM 개수, 렌더 시간 | 페이지 크기 조정, 가상화 |
| 지도 이동이 느림 | 요청 횟수, 핀 개수 | debounce, viewport 조회, 클러스터 |
| 가이드북 폴링 부하 | 주기, 열린 탭 수 | backoff, 서버 푸시 방식 검토 |

## 4. 피해야 할 조기 최적화

- 근거 없이 모든 컴포넌트에 `memo`, `useMemo`, `useCallback` 적용
- 필요한 화면보다 먼저 복잡한 전역 캐시 구성
- V1 요구가 없는 SSE, WebSocket, Service Worker 선도입
- 사용자 데이터 정합성을 해칠 수 있는 장시간 브라우저 캐시

## 5. 검증 체크리스트

- [ ] 개발·모바일 네트워크 조건에서 핵심 흐름 측정
- [ ] 모바일 Chrome·Safari와 넓은 데스크톱 viewport에서 앱 셸 크기·중앙 정렬·안전 영역 확인
- [ ] 빌드 산출물과 큰 의존성 확인
- [ ] 페이지 조회 요청은 화면 이탈 시 정리하고, 전역 생성 폴링은 종료 상태·앱 종료 시 정리되는지 확인
- [ ] 최적화 전후 동일 지표로 비교
