# V1 성능 최적화 방안

측정 없이 복잡한 최적화를 먼저 넣지 않는다. 이 문서는 현재 적용된 전략, 측정 기준과 병목이 확인된 뒤 도입할 선택지를 구분한다.

## 1. 측정 기준

### 사용자 지표

| 지표 | V1 목표 | 의미 |
| --- | ---: | --- |
| LCP | 2.5초 이하 | 주요 콘텐츠가 보이는 시간 |
| INP | 200ms 이하 | 클릭·입력에 대한 반응성 |
| CLS | 0.1 이하 | 예상하지 못한 layout 이동 |

- 배포 환경의 모바일 viewport에서 75 percentile을 기준으로 본다.
- 로그인, 취향 저장, 지도 첫 표시, 가이드북 목록, 생성 상태 화면을 대표 시나리오로 측정한다.
- Lighthouse는 실험실 진단에 사용하고 실제 사용자 지표와 구분한다.

### 프로젝트 보조 지표

- 초기 JavaScript gzip 크기: Sentry 도입 전 약 125KB, 도입 후 약 155KB다. 증가 원인은 운영 Error Monitoring SDK임을 확인했으며 이후 175KB를 넘거나 초기 로드 지연이 측정되면 dependency와 지연 초기화를 다시 검토한다.
- API: 화면별 요청 횟수, 중복 요청, timeout, 오류율을 확인한다.
- 지도: viewport 변경당 요청 수, 표시 마커·클러스터 수, drag 중 frame 저하를 확인한다.
- 가이드북: 열린 탭당 polling 횟수와 종료 상태 이후 추가 요청 여부를 확인한다.

## 2. 현재 적용된 최적화

### 데이터 페칭

- 지도 콘텐츠는 bounds·zoom·limit 조합을 key로 탭 메모리에 5분, 최대 30개 보관한다.
- 동일한 지도 요청이 진행 중이면 새 요청을 만들지 않고 Promise를 공유한다.
- 지도 API가 viewport와 zoom 기준 콘텐츠·클러스터를 반환하므로 전국 데이터를 브라우저에 한 번에 적재하지 않는다.
- 가이드북 목록은 cursor, 알림은 page·size로 제한해 대량 항목을 한 번에 렌더링하지 않는다.
- 화면 수명에 종속된 조회는 `AbortSignal`을 받을 수 있게 구성한 API가 있다.

### 인증과 화면 전환

- 검증된 ACTIVE 회원은 탭 메모리 캐시로 보호 화면을 즉시 표시하고 `/members/me`는 백그라운드 재검증한다.
- 회원 캐시는 새로고침을 넘겨 보존하지 않고 401·로그아웃·탈퇴 시 제거해 오래된 인증 상태를 장시간 사용하지 않는다.

### 비동기 작업

- 생성 상태는 전역 provider에서 2초 간격으로 조회해 화면 전환마다 polling이 중복 생성되지 않게 한다.
- 완료·실패·취소, 인증 오류와 provider 종료 시 timer와 요청을 정리한다.
- 생성 요청은 버튼 disabled와 `Idempotency-Key`를 함께 사용해 중복 제출 비용을 줄인다.

### 정적 리소스

- Vite가 production build에서 minify하고 hash가 포함된 asset 파일을 생성한다.
- 앱은 데스크톱에서도 모바일 폭 하나만 렌더링해 별도 데스크톱 layout 자산을 중복 제공하지 않는다.

## 3. 아직 적용하지 않은 개선안

| 징후 | 먼저 측정할 것 | 도입 후보 |
| --- | --- | --- |
| 첫 진입 bundle 증가 | route별 사용 코드, dependency 비중 | `React.lazy` 기반 route code splitting |
| 큰 이미지로 LCP 저하 | 원본 크기, decode 시간 | WebP/AVIF, `srcset`, width·height, lazy loading |
| 같은 조회 API 반복 | 요청 주체와 cache 수명 | 공통 요청 cache 또는 TanStack Query |
| 지도 drag 중 요청 과다 | idle event당 호출 수 | debounce, 이전 요청 abort, cache key 조정 |
| 마커 렌더링 지연 | DOM overlay 수, frame time | 서버 cluster 기준 조정, overlay 재사용 |
| 긴 목록 scroll 저하 | DOM node 수, render 시간 | page size 조정 후 필요 시 virtualization |
| 생성 polling 부하 | 탭 수, 평균 생성 시간 | backoff, visibility 기반 주기 조정, SSE 검토 |

- 현재 `App.tsx`는 화면을 정적으로 import하므로 route code splitting은 **계획 항목**이다.
- 전역 cache 라이브러리, SSE, WebSocket, Service Worker는 V1에서 미리 도입하지 않는다.
- `memo`, `useMemo`, `useCallback`은 React Profiler에서 반복 비용이 확인된 컴포넌트에만 적용한다.

## 4. 브라우저 캐싱 전략

- hash가 포함된 JS·CSS·이미지는 CDN에서 장기 cache하고 `index.html`은 새 배포 확인이 가능하도록 짧게 cache한다.
- 회원, 알림, 생성권, 가이드북처럼 개인화된 API 응답은 브라우저 HTTP cache에 장기 보관하지 않는다.
- 지도 콘텐츠 메모리 cache는 새로고침 시 사라지며 사용자 세션 간 공유하지 않는다.
- API 오류 응답과 OAuth callback URL을 Service Worker나 CDN cache 대상으로 만들지 않는다.
- 실제 Cache-Control은 CloudFront·origin 응답을 함께 확인하고 FE 코드만으로 적용됐다고 판단하지 않는다.

## 5. 시나리오별 확인

### 로그인 → 취향 → 지도

1. 로그인 화면에서 사용하지 않는 가이드북·지도 코드 비중을 bundle analyzer로 확인한다.
2. OAuth 완료 뒤 회원·취향 요청이 직렬로 필요한지 waterfall을 확인한다.
3. 지도 첫 표시에서 SDK load, 위치 권한, 콘텐츠 요청 중 LCP 병목을 구분한다.

### 지도 이동

1. 같은 viewport 요청이 cache 또는 진행 중 요청 병합으로 줄어드는지 확인한다.
2. 낮은 zoom에서 개별 마커 대신 cluster가 렌더링되는지 확인한다.
3. bottom sheet drag와 지도 pan 중 long task와 dropped frame을 확인한다.

### 가이드북 생성

1. 생성 화면을 벗어나도 polling이 하나만 유지되는지 확인한다.
2. 완료·실패·취소 이후 network 요청이 중단되는지 확인한다.
3. background tab에서 요청량이 문제가 되면 visibility 또는 backoff를 검토한다.

## 6. 적용 순서

1. 배포 환경에서 기준 지표와 network trace를 남긴다.
2. 사용자 영향이 큰 병목 하나를 선택한다.
3. 변경 전후를 같은 기기·network·시나리오로 비교한다.
4. 정합성, 접근성, 오류 복구가 나빠지지 않았는지 테스트한다.
5. 실제 개선이 확인된 전략만 유지하고 V1 문서에 결과를 갱신한다.
