# V1 프론트엔드 개발 표준 및 구조

## 1. 기술 기준

| 구분 | 현재 선택 | 역할 |
| --- | --- | --- |
| 언어 | TypeScript strict | API·상태·컴포넌트 계약의 정적 검증 |
| UI | React 19 | 사용자 상태 기반 화면 구성 |
| 라우팅 | React Router 7 | 공개·온보딩·ACTIVE 화면 분기 |
| HTTP | Axios | 세션 cookie, timeout, 오류 응답 처리 |
| 빌드 | Vite 8 | 개발 서버와 프로덕션 번들 생성 |
| 테스트 | Vitest, Testing Library, jsdom | 함수·API 계약·사용자 상호작용 검증 |
| 정적 검사 | TypeScript, oxlint | 타입·코드 규칙 검사 |
| 행동 분석 | Google Analytics | 로그인·가이드북 생성 흐름 집계 |
| 오류 관측 | Sentry | 운영 예외와 원본 stack trace 확인 |

새 라이브러리는 현재 코드로 해결하기 어려운 반복 문제가 확인될 때 추가한다. V1에는 별도 전역 상태·서버 상태 라이브러리를 사용하지 않는다.

## 2. 디렉터리와 책임

```text
src/
├── app/                 # Router와 전역 Provider 조합
├── features/
│   └── <domain>/
│       ├── api/         # HTTP 호출, DTO 타입·응답 검증
│       ├── model/       # 화면 밖에서도 유지할 상태와 순수 규칙
│       └── ui/          # 도메인 화면·컴포넌트·스타일
├── pages/               # 단순 조합 또는 임시 페이지
├── shared/
│   ├── api/             # Axios, CSRF, 공통 응답 타입
│   ├── config/          # 라우트·환경 설정
│   └── ui/              # 실제로 여러 기능에서 재사용하는 UI
├── styles/              # 전역 token과 공통 layout
└── test/                # 공통 테스트 setup
```

- 기능 전용 코드는 `features/<domain>`에 둔다.
- API 호출을 UI 컴포넌트에 직접 흩뿌리지 않고 기능별 `api` 모듈에 모은다.
- 여러 기능에서 실제 재사용되는 코드만 `shared`로 올린다.
- `app`은 provider와 route 조합을 담당하고 도메인 비즈니스 규칙을 갖지 않는다.
- 파일이 커졌다는 이유만으로 계층을 늘리지 않고 책임이 분리될 때 나눈다.

## 3. TypeScript·React 규칙

- `strict`를 유지하고 `any` 대신 서버 응답은 `unknown`에서 검증한다.
- 서버 DTO와 화면 파생 상태가 다르면 API 계층 또는 순수 함수에서 변환한다.
- 서버 Enum 문자열은 union type으로 제한하되 런타임 응답도 검증한다.
- Effect는 외부 시스템 동기화에 사용하고 계산 가능한 값은 render 또는 `useMemo` 없이 우선 계산한다.
- 타이머, event listener, 진행 중 요청은 화면·provider 수명에 맞춰 cleanup한다.
- `memo`, `useMemo`, `useCallback`은 일괄 적용하지 않고 identity 유지나 측정된 렌더 비용 근거가 있을 때 사용한다.
- URL, storage key, 반복되는 정책값은 의미 있는 상수로 관리한다.

## 4. API·인증·오류 처리

- Axios 공통 인스턴스는 `withCredentials: true`를 유지한다.
- JavaScript 저장소에 서비스 세션 원문을 저장하지 않는다.
- POST·PUT·PATCH·DELETE 전에 공통 CSRF 모듈을 통해 token을 준비한다.
- 서버 성공·오류 envelope를 구분하고 필수 필드를 런타임 검증한다.
- 401, 403, 409, 422와 네트워크·5xx를 같은 오류로 처리하지 않는다.
- OAuth code, session, CSRF 값, 개인정보를 console·analytics·Issue·PR에 남기지 않는다.
- 사용자가 재시도해도 안전한 요청과 그렇지 않은 상태 변경 요청을 구분한다. 생성 요청은 서버의 멱등키 계약을 따른다.

## 5. 모바일 웹 앱·반응형 디자인

- V1은 모바일 중심 웹 앱이며 데스크톱에서도 모바일 앱 폭을 중앙에 표시한다.
- V3까지 데스크톱 전용 다단·확장 layout을 만들지 않는다.
- `app-shell` 경계 안에서 `width: 100%`, 최대 폭, `margin-inline: auto`를 사용한다.
- 루트와 `app-shell`은 `100vh` → `100svh` → `100dvh` 순으로 fallback을 두고, 각 페이지에서 뷰포트 높이를 중복 선언하지 않는다.
- 지도는 현재 뷰포트 높이에 고정하고 넘치는 내용을 숨긴다. 일반 페이지는 콘텐츠가 뷰포트보다 길 때만 문서 스크롤을 허용한다.
- 하단 navigation은 뷰포트 하단에 고정하고, navigation이 있는 페이지 본문에는 navigation 높이와 safe area를 합한 하단 여백을 둔다.
- 모달·bottom sheet·하단 navigation에 `env(safe-area-inset-*)`를 반영해 iOS 홈 인디케이터 영역과 겹치지 않게 한다.
- 터치 target은 충분한 크기와 간격을 제공하고 hover만으로 의미를 전달하지 않는다.
- 지도와 bottom sheet는 모바일 viewport, 브라우저 주소창 변화, 가로 스크롤을 함께 확인한다.

레이아웃 변경 시 로그인·지도·가이드북·마이페이지·설정·알림 화면을 모바일 Chrome/Safari와 데스크톱의 좁은 viewport에서 확인한다. 짧은 화면은 하단 빈 영역으로 스크롤되지 않아야 하고, 긴 화면은 콘텐츠와 하단 navigation이 겹치지 않아야 한다.

## 6. 코드 컨벤션과 품질 검사

- 사용자 문구는 한국어로 쓰고 코드 식별자·API 필드는 계약에 맞는 영어를 사용한다.
- 접근 가능한 `button`, `a`, `input`, heading을 우선하며 클릭 가능한 `div`를 만들지 않는다.
- icon-only button에는 동작을 설명하는 `aria-label`을 제공한다.
- loading, empty, success, error와 disabled 상태를 필요한 수준으로 구현한다.
- 커밋 전 다음 명령을 각각 실행한다.

```bash
npm run typecheck
npm run lint
npm test -- --run
npm run build
```

## 7. 브라우저 지원과 Polyfill

- 지원: 최신 Chrome, Safari, Edge와 해당 엔진 기반 모바일 브라우저의 현재 주요 버전.
- 미지원: Internet Explorer와 오래된 WebView.
- V1은 범용 polyfill bundle을 넣지 않는다. 지원 브라우저에서 부족한 기능이 확인되면 해당 기능만 도입하고 bundle 영향을 기록한다.
- 위치 권한, cookie, `100dvh`, safe area, iframe sandbox처럼 브라우저 차이가 큰 기능은 실제 기기 또는 동일 엔진에서 확인한다.

## 8. 환경 변수와 보안

- 클라이언트에 노출 가능한 값만 `VITE_` prefix로 사용한다.
- 카카오 JavaScript key처럼 브라우저용 공개 식별자도 허용 domain 제한을 함께 설정한다.
- secret, REST API secret, Admin key는 FE 환경 변수나 bundle에 넣지 않는다.
- `.env.example`에는 키 이름과 설명만 두고 실제 값을 커밋하지 않는다.

## 9. SEO·분석

- 인증 후 사용하는 모바일 웹 앱이므로 V1의 우선순위는 검색 노출보다 정확한 title, description, favicon과 공유 가능한 공개 진입 URL이다.
- 개인정보·OAuth code·내부 오류 상세를 URL이나 analytics event에 넣지 않는다.
- Google Analytics는 page view와 필요한 사용자 행동만 수집하고 계정 식별값, 이메일, 닉네임을 전송하지 않는다.
- Sentry는 production과 DSN이 있는 경우에만 활성화하며 user, cookie, header, body와 URL query 수집을 비활성화한다.
- source map은 인증된 배포 build에서 Sentry에 업로드한 뒤 삭제하고 S3·CloudFront에는 제공하지 않는다.
- 이벤트 목록, 환경변수 역할과 배포 검증은 `관측성-운영.md`를 따른다.
- 공개 콘텐츠 검색 노출이 제품 요구가 되면 SSR/SSG, Open Graph, canonical URL을 별도 기술 검토한다.

## 10. 테스트 전략

| 계층 | 우선 검증 |
| --- | --- |
| 순수 함수 | 입력, 날짜·인원·선택 개수, 경계값 |
| API 모듈 | 응답 계약, 대표 오류, timeout·취소, CSRF |
| 컴포넌트 | 사용자의 클릭·입력과 보이는 결과 |
| 라우팅·Provider | 비로그인, ONBOARDING, ACTIVE, 세션 만료, 폴링 종료 |
| 브라우저 확인 | 실제 OAuth, cookie, 위치 권한, Kakao Maps, 모바일 safe area |

구현 세부 줄 수를 채우기보다 실패하면 핵심 사용자 흐름이 깨지는 계약을 우선한다. mock 기반 테스트가 실제 cookie·OAuth·지도 SDK를 증명하지 않으므로 배포 전 브라우저 확인을 별도로 수행한다.
